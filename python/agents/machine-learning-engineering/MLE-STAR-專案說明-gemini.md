# MLE-STAR 專案說明

本文件旨在詳細說明 MLE-STAR (Machine Learning Engineering Agent via Search and Targeted Refinement) 專案，並回答關於其設計、實作和相關機器學習概念的問題。

## 第一部分：專案總覽

### 1. 專案用途是什麼？
此專案是一個**自動化機器學習工程師 (Automated Machine Learning Engineer)**。

您可以把它想像成一個智慧型機器人，它的目標是**自動解決機器學習問題**。對於一個大學生程度、但沒有機器學習背景的人來說，可以這樣理解：

傳統上，若要解決一個數據預測問題（例如，根據房子的特徵預測房價），需要一位人類專家（機器學習工程師）。這位專家需要：
1.  **清理數據**：處理數據中的錯誤或缺失值。
2.  **特徵工程**：從原始數據中創造出對預測更有幫助的新特徵。
3.  **選擇模型**：從眾多機器學習模型（如 `LightGBM`, `RandomForest`）中挑選合適的。
4.  **編寫程式**：用 Python 等語言編寫訓練模型的程式。
5.  **反覆實驗**：不斷調整程式和模型參數，以獲得最準確的預測結果。

這個過程非常耗時且需要大量專業知識。

**MLE-STAR 專案的目的就是將上述流程自動化**。使用者只需要提供數據和問題描述（例如，「這是一個房價預測問題，請用這些數據訓練一個模型」），這個專案（代理程式）就會自動上網搜尋最佳實踐、編寫程式碼、進行實驗、除錯、並逐步優化，最終產出一個高品質的機器學習模型和預測結果，其表現甚至能媲美人類專家在 Kaggle 等數據競賽中的水準。

### 2. 專案的 Input/Output 是什麼？
-   **Input (輸入):**
    1.  **任務描述檔案 (`task_description.txt`)**: 一個純文字檔，用自然語言描述機器學習任務的目標。例如：「這是一個迴歸任務，目標是根據多種人口、地理和財務特徵，預測加州各區域的房價中位數。」
    2.  **數據檔案 (例如 `train.csv`, `test.csv`)**: 標準的數據集檔案。`train.csv` 包含帶有正確答案（目標值）的數據，用於訓練機器學習模型；`test.csv` 包含沒有答案的數據，用於生成最終的預測結果。

-   **Output (輸出) / 最終產出:**
    1.  **完整的 Python 訓練程式 (`final_solution.py`)**: 一個可以直接運行的 Python 腳本。這是整個專案最有價值的產出之一，它包含了從數據讀取、清理、特徵工程到模型訓練和預測的所有邏輯。這份程式碼是經過多輪自動優化後的最終版本。
    2.  **預測結果檔案 (`submission.csv`)**: 一個 CSV 檔案，包含了對 `test.csv` 中每一行數據的預測結果。這個檔案的格式通常符合 Kaggle 等競賽平台的要求，可以直接上傳以獲得評分。
    3.  **中間過程與日誌 (Workspace)**: 專案在 `workspace` 目錄下會儲存所有中間步驟產生的程式碼、實驗結果、日誌等。這對於理解代理程式的「思考過程」和除錯非常有幫助。

    **作用**: 最終產出的程式碼和預測結果，可以直接應用於實際業務或參加數據科學競賽，解決具體的預測問題。

### 3. 專案用到哪些 LLM？分別用在哪裡？
本專案的核心是透過大型語言模型 (LLM) 來模擬人類工程師的思考和編碼行為。專案在多個環節使用 LLM (可配置，例如 Gemini 系列模型)，每個環節的 LLM 扮演不同角色：

1.  **`A_retriever` (模型檢索員)**:
    -   **使用位置**: 初始化階段。
    -   **LLM 作用**: 接收任務描述後，LLM 會**生成搜尋關鍵字** (例如 "california housing price prediction python code example")，並利用 Google 搜尋工具上網查找相關的機器學習模型和程式碼範例。然後，LLM 會**解析搜尋結果**，提取出最有潛力的模型（如 LightGBM、RandomForest）及其範例程式碼。

2.  **程式碼生成與除錯代理程式**:
    -   **使用位置**: 初始化、優化和整合階段。
    -   **LLM 作用**:
        -   **生成完整程式**: 將 `A_retriever` 找到的零散程式碼範例，改編成一個能在此專案數據上運行的完整、獨立的訓練腳本。
        -   **修復錯誤 (Debug)**: 當產生的程式碼運行失敗時，系統會捕捉錯誤訊息 (Traceback)，並將**錯誤訊息和原始程式碼**一起發送給 LLM，要求它**修復這個錯誤**。這個過程會循環直到程式碼能成功運行。

3.  **`A_abl` (消融研究員)**:
    -   **使用位置**: 優化階段 (Refinement)。
    -   **LLM 作用**: LLM 接收一份完整的訓練程式碼，並被要求**生成「消融研究」版本的程式碼**。也就是說，LLM 需要策略性地註解掉或移除程式中的某些區塊（例如某個特徵工程步驟），以測試該區塊對最終結果的重要性。

4.  **`A_extractor` & `A_planner` (分析師與計劃員)**:
    -   **使用位置**: 優化階段。
    -   **LLM 作用**:
        -   **分析結果**: LLM 負責**解讀消融研究的結果**，找出對模型性能影響最大的「關鍵程式碼區塊」。
        -   **制定優化計劃**: 針對這個關鍵區塊，LLM 會**腦力激盪並提出一個改進計劃**。例如：「目前的特徵縮放效果不好，計劃嘗試以下三種策略：1. 改用 `MinMaxScaler`；2. 增加 `RobustScaler`；3. 移除縮放步驟，直接使用原始特徵。」

5.  **`A_ensemble` (模型整合專家)**:
    -   **使用位置**: 整合階段 (Ensemble)。
    -   **LLM 作用**: LLM 接收多個經過優化的不同模型方案，並被要求**設計一個整合策略**，將這些模型的預測結果組合起來，以獲得比任何單一模型都更好的最終預測。例如，LLM 可能會提出「對模型 A 和模型 B 的預測結果進行加權平均，權重分別為 0.7 和 0.3」。接著，它會生成實作這個策略的程式碼。

### 4. Kaggle 的 "california-housing-prices" 與本專案有何相關？
**直接相關**。本專案使用 Kaggle 上的 "california-housing-prices" 數據集作為一個**內建的範例任務**，用來展示和測試整個自動化流程的能力。

-   **數據來源**: 專案中的 `tasks/california-housing-prices` 目錄下的 `train.csv` 和 `test.csv` 就是來自這個 Kaggle 任務。
-   **任務目標**: 專案解決的問題——預測加州房價——與該 Kaggle 任務的目標完全一致。
-   **基準測試**: 透過在這個公開、標準化的任務上運行，開發者可以評估 MLE-STAR 自動產生的模型能達到什麼樣的水平，是否能與人類參賽者一較高下。

簡單來說，"california-housing-prices" 是 MLE-STAR 專案用來「練兵」和「考試」的靶場。

## 第二部分：技術細節與名詞解釋

### 1. 什麼是「機器學習模型」？
「機器學習模型」可以被理解為一個**數學函數或演算法**，它能從數據中**學習**出隱藏的模式或規則。

想像一下，你正在教一個小朋友如何區分貓和狗。你給他看很多貓和狗的照片（**數據**），並告訴他每張照片裡是什麼（**標籤**）。經過一段時間的學習，小朋友的大腦中就形成了一套判斷規則（例如「有尖耳朵、長鬍鬚的可能是貓」）。這個小朋友腦中的「判斷規則」就是一個**模型**。

在電腦世界裡，「機器學習模型」就是這個「判斷規則」的數學表達式。我們透過一個稱為「**訓練**」的過程，將大量的數據（例如房子的特徵和對應的房價）餵給這個模型。模型會自動調整內部的參數，直到它能根據輸入的特徵，給出非常接近真實房價的預測。訓練完成後，這個模型就可以用來預測從未見過的新房子的價格了。

### 2. 什麼是 "LightGBM"、"XGBoost"、"RandomForest"？
這三者都是目前業界非常流行且強大的**機器學習模型**，特別擅長處理表格類型的數據（像 Excel 或 CSV 檔案那樣的數據）。它們都屬於「**決策樹**」模型的變種。

-   **RandomForest (隨機森林)**:
    -   **比喻**: 想像一下，為了做一個重要決定，你不會只問一位專家，而是去問很多位專家，然後綜合他們的意見。
    -   **原理**: 隨機森林就是同時建立數百甚至數千棵「決策樹」（決策樹就像一個做決策的流程圖）。對於一個預測任務，每棵樹都會給出自己的答案，而隨機森林最終的答案，就是綜合所有樹的答案得出的結果（例如，取平均值或投票）。這大大提高了預測的準確性和穩定性。

-   **XGBoost (極限梯度提升)** 和 **LightGBM (輕量級梯度提升機)**:
    -   **比喻**: 這兩者更像一個精英團隊，而不是一群獨立的專家。團隊中的第一個成員先做一個初步預測，第二個成員專門學習如何修正第一個成員的錯誤，第三個成員再學習如何修正前兩者結合後的錯誤，以此類推。
    -   **原理**: 它們都屬於「梯度提升 (Gradient Boosting)」框架。模型也是由多棵決策樹組成，但這些樹是循序建立的，後一棵樹的目標是彌補前面所有樹的不足。這種方式通常能達到比隨機森林更高的準確度。
    -   **區別**: LightGBM 是微軟開發的，相較於 XGBoost，它在訓練速度上通常更快，記憶體佔用也更少，因此得名「輕量級」。在許多情況下，兩者的準確度不相上下。

### 3. 從哪裡可以找到「機器學習模型」與「模型範例」？
對於開發者和 MLE-STAR 這樣的代理程式來說，主要有以下幾個來源：

1.  **Kaggle (https://www.kaggle.com)**:
    -   這是最重要的資源之一。Kaggle 是全球最大的數據科學競賽平台。參賽者會分享他們的解決方案，這些被稱為 "Notebooks"。
    -   **優點**: 你可以找到針對特定問題（如房價預測）的、包含完整程式碼、數據處理和模型訓練邏輯的高質量範例。MLE-STAR 的 `A_retriever` 代理程式很可能就在搜尋類似 "Kaggle california housing LightGBM" 的內容。

2.  **Scikit-learn 官方文檔 (https://scikit-learn.org/stable/auto_examples/index.html)**:
    -   Scikit-learn 是 Python 中最基礎、最重要的機器學習函式庫。它的官方文檔提供了幾乎所有經典模型的標準用法和程式碼範例。
    -   **優點**: 程式碼最標準、最權威，適合學習模型的基礎用法。

3.  **模型官方文檔 (例如 LightGBM, XGBoost)**:
    -   LightGBM: https://lightgbm.readthedocs.io/en/latest/Examples.html
    -   XGBoost: https://xgboost.readthedocs.io/en/latest/python/examples.html
    -   **優點**: 提供了更進階的用法和參數設定範例。

4.  **技術部落格和教學網站**:
    -   例如 Medium (Towards Data Science), Machine Learning Mastery, Analytics Vidhya 等。開發者經常在這些平台上分享他們的專案和程式碼。

MLE-STAR 的 `A_retriever` 透過 Google 搜尋，實際上就是在彙總上述這些來源的資訊。

### 4. 初始解決方案的數量如何影響專案結果？
初始解決方案的數量由設定檔中的 `num_solutions` 參數控制。這個數量會對專案結果產生顯著影響：

-   **增加數量的好處**:
    1.  **探索更多可能性**: 每個初始解決方案都是從一個獨立的網路搜尋和模型選擇過程開始的。產生多個方案，相當於從不同的起點去探索解決問題的路徑。一個方案可能從 LightGBM 開始，另一個可能從 RandomForest 開始，這增加了找到更優解的機會。
    2.  **提升最終整合 (Ensemble) 的效果**: 模型整合的效果通常在於「差異化」。如果將多個性能不錯但思路各異的模型組合起來，其效果往往比單一模型更好。擁有多個初始解決方案，經過各自獨立的優化後，它們之間的差異性會更大，為最終的 `A_ensemble` 提供了更豐富、更多樣的「原料」，從而更有可能整合出一個強大的最終模型。

-   **增加數量的代價**:
    1.  **資源消耗增加**: 每個解決方案都需要獨立進行初始化、優化等一系列步驟，這會消耗大量的計算資源（CPU/GPU）和 LLM API 呼叫次數。如果 `num_solutions` 設定為 3，則總資源消耗大約是設定為 1 的三倍。
    2.  **時間成本增加**: 整個流程的運行時間會顯著加長。

**結論**: `num_solutions` 是一個權衡。較高的數值（如 2 或 3）能增加找到頂尖解決方案的機率，但成本也更高。對於追求極致性能的競賽場景，設定較高的值是值得的。對於需要快速得到一個可用模型的場景，設定為 1 則更經濟高效。

### 5. 什麼是「消融研究」(ablation study)？
「消融研究」是一種分析和理解複雜系統（在這裡指機器學習模型）的方法。其核心思想是**「透過移除部分組件，來觀察系統性能的變化，從而判斷該組件的重要性」**。

**比喻**: 想像你有一輛賽車，你想知道哪個零件對速度的貢獻最大。你可以：
1.  先測一下完整賽車的最高時速（基準性能）。
2.  然後，**移除**尾翼，再測一次最高時速。發現速度下降了很多。
3.  接著，把尾翼裝回去，**移除**渦輪增壓器，再測一次。發現速度急劇下降。

透過比較，你發現移除渦輪增壓器比移除尾翼對速度的影響更大，因此得出結論：**渦輪增壓器是比尾翼更關鍵的組件**。

在 MLE-STAR 專案中，`A_abl` 代理程式所做的就是這件事：
1.  它有一個完整的 Python 訓練程式（基準性能）。
2.  它請求 LLM 生成一個新版本，其中**註解掉了「數據標準化」** 的程式碼區塊，然後運行並記錄性能分數。
3.  它再請求 LLM 生成另一個版本，其中**註解掉了「處理缺失值」** 的程式碼區塊，然後運行並記錄分數。

透過比較這些「殘缺」版本的性能與基準性能的差異，`A_abl` 就能找出對模型準確度影響最大的程式碼區塊，並將其作為下一步優化的重點目標。

### 6. 將「多個模型組合（ensemble）以獲得更好的預測結果」。組合了哪些模型？
在這個專案中，被組合 (ensemble) 的模型是**經過 `refinement` (優化) 階段後，由不同 `init_solution_gen_agent` 並行實例產生的最終模型**。

讓我們回顧一下流程：
1.  `num_solutions` 參數設定為 N (例如 N=2)。
2.  系統會並行啟動 N 個**獨立的**解決方案生成流程。
3.  **流程 1**: 可能從網路搜尋到 `LightGBM` 開始，經過多輪優化，最終得到一個高度優化的 `LightGBM` 模型程式 (`train_final_1.py`)。
4.  **流程 2**: 可能從網路搜尋到 `RandomForest` 開始，經過多輪優化，最終得到一個高度優化的 `RandomForest` 模型程式 (`train_final_2.py`)。
5.  **整合階段**: `A_ensemble` 代理程式會接收 `train_final_1.py` 和 `train_final_2.py` 這兩個成果。它要組合的就是這兩個**最終優化過的模型**。

`A_ensemble` 會利用 LLM 來設計組合策略，例如：
-   **簡單平均**: 將 `LightGBM` 的預測結果和 `RandomForest` 的預測結果直接相加後除以 2。
-   **加權平均**: 根據它們各自的性能，給予不同的權重，例如 `0.7 * LightGBM_pred + 0.3 * RandomForest_pred`。
-   **元模型 (Meta-model)**: 將兩個模型的預測結果作為新的特徵，再訓練一個簡單的線性模型來做出最終的預測。

所以，組合的不是初始模型，而是各自「進化」到最終形態的高度優化過的模型。

### 7. 什麼是「資料清理」、「特徵工程」、「模型選擇」、「參數調整」、「模型整合」？
這些是機器學習專案中最核心的幾個步驟：

-   **資料清理 (Data Cleaning)**:
    -   **定義**: 處理數據中的問題，使其變得乾淨、可用。
    -   **任務**: 包括處理**缺失值**（例如，某個房子的年份數據是空的，需要用平均值或中位數填補）、處理**異常值**（例如，一個房價是 0 或極大，可能是錯誤數據）、統一數據格式等。

-   **特徵工程 (Feature Engineering)**:
    -   **定義**: 從原始數據中創造出新的、對模型預測更有幫助的特徵 (feature)。這是機器學習中最具創造性也最關鍵的一步。
    -   **任務**:
        -   **組合特徵**: 例如，從「總房間數」和「家庭數」可以計算出新的特徵「平均每戶房間數」。
        -   **轉換特徵**: 對偏態分布的數據（如收入）取對數，使其更接近常態分布，有助於模型學習。
        -   **編碼類別特徵**: 將文字類型的特徵（如「離海遠近」）轉換成模型能理解的數字（如 0, 1, 2, 3）。

-   **模型選擇 (Model Selection)**:
    -   **定義**: 根據任務的類型（如迴歸、分類）、數據的特點（數據量大小、特徵維度）和業務需求（對速度、準確度的要求），從眾多機器學習模型中選擇最合適的一個或幾個。
    -   **任務**: 在本專案中，`A_retriever` 透過網路搜尋來輔助完成這一步，找出當前問題的常用SOTA（State-of-the-art）模型。

-   **參數調整 (Parameter Tuning / Hyperparameter Tuning)**:
    -   **定義**: 幾乎所有機器學習模型都有一組「超參數」(Hyperparameters)，這些不是模型從數據中學到的，而是需要由工程師手動設定的。例如，隨機森林的「決策樹數量」。
    -   **任務**: 尋找一組最佳的超參數組合，以最大化模型的性能。這通常是一個非常耗時的試誤過程。MLE-STAR 的優化循環中，LLM 提出的改進計劃就可能包含調整這些參數。

-   **模型整合 (Model Ensembling)**:
    -   **定義**: 將多個獨立訓練好的模型組合起來，以獲得比任何單一模型都更強大、更穩定的預測能力。
    -   **任務**: 正如問題 6 所述，`A_ensemble` 代理程式專門負責此任務，設計並實作模型組合的策略。

### 8. 「要嘗試的模型候選數量」中的「模型」是指什麼？
這裡的「模型」指的是**機器學習模型 (Machine Learning Model)**，例如 `LightGBM`, `XGBoost`, `RandomForest` 等，**不是指 LLM**。

這個數量由設定檔中的 `num_model_candidates` 參數決定。

**決定方式**:
在 `initialization` 階段，`A_retriever` 代理程式會上網搜尋，並請 LLM 列出一個它認為適合當前任務的多個機器學習模型候選列表。`num_model_candidates` 參數就是告訴代理程式：「從這個列表裡，挑選前 N 個候選來進行下一步的評估。」

例如，如果 `A_retriever` 搜尋後認為 `LightGBM`, `XGBoost`, `RandomForest`, `CatBoost` 這四個模型都不錯，而 `num_model_candidates` 設定為 2，那麼系統就只會挑選 `LightGBM` 和 `XGBoost` 這兩個排名最靠前的候選，為它們分別生成完整的訓練程式碼並進行評估，以決定哪個作為初始解決方案的基礎。

這個參數的設定也是一個權衡：
-   **較高的值**: 探索更多不同類型的機器學習模型，增加找到最佳基線模型的機會。
-   **較低的值**: 減少評估時間和資源消耗，更快地進入優化階段。

### 9. 調整配置參數會有哪些影響？
在 `README.md` 和 `shared_libraries/config.py` 中可以看到多個配置參數，它們對專案行為有直接影響：

-   **`task_name`**:
    -   **說明**: 要執行的任務名稱，對應 `tasks` 目錄下的一個子目錄。
    -   **影響**: 決定了代理程式要讀取哪個任務的描述、訓練數據和測試數據。更改此參數會讓代理程式解決一個全新的問題。

-   **`task_type`**:
    -   **說明**: 機器學習問題的類型，如 `Tabular Regression` (表格迴歸) 或 `Tabular Classification` (表格分類)。
    -   **影響**: 這個資訊會被提供給 LLM，幫助它在搜尋模型 (`A_retriever`) 和制定計劃 (`A_planner`) 時做出更合理的決策。例如，為迴歸問題選擇 RMSE 作為評估指標，為分類問題選擇準確率 (Accuracy) 或 F1-score。

-   **`metric_name`**:
    -   **說明**: 評估模型好壞的具體指標，例如 `neg_root_mean_squared_error` (負均方根誤差)。
    -   **影響**: 這是所有優化和選擇的**核心依據**。代理程式會根據這個指標的得分來判斷一次改進是否成功、哪個模型更好。選錯指標會導致整個優化過程朝錯誤的方向進行。

-   **`lower`**:
    -   **說明**: 一個布林值，指出評估指標 (`metric_name`) 是否越低越好。
    -   **影響**: 至關重要。例如，對於「誤差」(Error) 指標，值越低越好 (`lower=True`)；對於「準確率」(Accuracy) 指標，值越高越好 (`lower=False`)。如果設定錯誤，代理程式會把性能變差的改動當成好的改動。

-   **`num_solutions`**:
    -   **說明**: 要並行生成的初始解決方案的數量。
    -   **影響**: 如問題 4 所述，影響探索的廣度和最終整合的效果，同時也直接影響資源消耗和時間。

-   **`num_model_candidates`**:
    -   **說明**: 在初始化階段，從網路搜尋結果中挑選前 N 個模型候選進行評估。
    -   **影響**: 如問題 8 所述，影響初始模型選擇的範圍。

-   **`outer_loop_round`**:
    -   **說明**: 在 `refinement` 階段，進行幾輪「消融研究 -> 鎖定區塊 -> 優化」的**外層循環**。
    -   **影響**: 決定了對一個解決方案進行多少次「大版本」的迭代。越高的值意味著越深度的優化，但時間也越長。

-   **`inner_loop_round`**:
    -   **說明**: 在 `refinement` 的每一輪外層循環中，針對鎖定的關鍵程式碼區塊，嘗試多少種不同的改進**內層循環**。
    -   **影響**: 決定了在一個優化點上的探索廣度。越高的值意味著會嘗試更多的改進策略。

-   **`agent_model`**:
    -   **說明**: 指定所有代理程式使用的 LLM 模型，例如 `gemini-1.5-pro` 或 `gemini-1.5-flash`。
    -   **影響**: 直接影響代理程式的「智慧」程度和成本。使用更強大的 LLM（如 Pro）可能會產生更高質量的程式碼和計劃，但成本也更高、速度可能更慢。使用較輕量的 LLM（如 Flash）則更經濟高效。

### 10. 所謂「多輪優化改進的完整訓練程式」請詳細說明程式邏輯。
這指的是在 `refinement` 階段，透過內外雙層循環，對初始的訓練程式 (`train0.py`) 進行迭代改進的過程。

**程式邏輯詳解**:

假設我們從 `train0.py` 開始，`outer_loop_round` 設定為 2，`inner_loop_round` 設定為 3。

**第一輪外層循環 (產生 `train1.py`)**:
1.  **輸入**: `train0.py` 程式碼及其性能分數 (例如 RMSE=0.55)。
2.  **消融研究 (`A_abl`)**:
    -   代理程式分析 `train0.py`，並要求 LLM 生成一個進行消融研究的特殊版本 `ablation_0.py`。
    -   運行 `ablation_0.py`，結果顯示「特徵縮放」這個步驟對性能影響最大。
3.  **鎖定目標與制定計劃 (`A_extractor`, `A_planner`)**:
    -   代理程式根據消融結果，從 `train0.py` 中**提取**出與「特徵縮放」相關的程式碼區塊。
    -   LLM 針對這個區塊**制定一個初步改進計劃**，例如：「計劃 A：將 `StandardScaler` 更換為 `MinMaxScaler`」。
4.  **內層循環 (嘗試 3 種改進)**:
    -   **第 1 次嘗試**:
        -   **實作計劃 A**: LLM 將 `train0.py` 中的 `StandardScaler` 程式碼替換為 `MinMaxScaler`，生成 `train0_improve0.py`。
        -   運行並評估，得到分數 (例如 RMSE=0.54，有進步)。
        -   **優化計劃**: LLM 看到進步，提出**新計劃 B**：「`MinMaxScaler` 不錯，試試 `RobustScaler`，它對異常值更不敏感」。
    -   **第 2 次嘗試**:
        -   **實作計劃 B**: LLM 將 `train0.py` 中的 `StandardScaler` 替換為 `RobustScaler`，生成 `train0_improve1.py`。
        -   運行並評估，得到分數 (例如 RMSE=0.53，進步更大)。
        -   **優化計劃**: LLM 看到更大進步，提出**新計劃 C**：「`RobustScaler` 效果很好，再試試結合它與多項式特徵」。
    -   **第 3 次嘗試**:
        -   **實作計劃 C**: LLM 實作計劃 C，生成 `train0_improve2.py`。
        -   運行並評估，得到分數 (例如 RMSE=0.535，反而變差了)。
5.  **選擇最佳改進**: 比較三次嘗試的結果，發現第 2 次嘗試 (`train0_improve1.py`) 的分數 0.53 是最好的。
6.  **產出**: 系統將 `train0_improve1.py` 的內容儲存為 `train1.py`。第一輪外層循環結束。

**第二輪外層循環 (產生 `train2.py`)**:
-   流程與第一輪完全相同，但這次的**輸入**變成了 `train1.py` 及其性能分數 0.53。代理程式會在此基礎上，尋找新的、下一個最值得優化的點，並重複上述的「消融->計劃->實作->優化計劃」的循環。

經過 `outer_loop_round` 輪的迭代後，產生的最終程式就是「多輪優化改進的完整訓練程式」。它是在初始方案的基礎上，由 LLM 像一位真正的工程師一樣，透過不斷實驗和修正，一步步「進化」而來的。

### 11. 各 Agent 在此範例中呼叫 LLM 的次數如何決定？
LLM 的呼叫次數不是一個固定的數字，而是由**配置參數**和**執行過程中的事件**共同決定的。

-   **`A_retriever`**:
    -   **呼叫次數**: 在每個並行解決方案 (`num_solutions`) 的初始化階段**固定呼叫 1 次**。
    -   **如何修改**: 次數與 `num_solutions` 成正比。如果 `num_solutions=2`，則總共呼叫 2 次。

-   **`A_abl` (消融研究)**:
    -   **呼叫次數**: `num_solutions` * `outer_loop_round` * `(1 + 平均除錯次數)`。
        -   在每個外層循環中，`A_abl` 會被呼叫 1 次來生成消融程式碼。
        -   如果生成的程式碼有 bug，`debug_agent` 會介入，**每次除錯都會額外呼叫 LLM**。
    -   **如何修改**: 減少 `num_solutions` 或 `outer_loop_round` 會直接減少呼叫次數。改善 LLM 的程式碼生成能力（例如，使用更強的模型或改進 Prompt）可以減少除錯次數。

-   **`A_extractor` & `A_planner` (提取與計劃)**:
    -   **呼叫次數**: `num_solutions` * `outer_loop_round` * `(1 + inner_loop_round)`。
        -   每個外層循環開始時，呼叫 1 次來**提取區塊並制定初始計劃**。
        -   在內層循環中，每次嘗試改進後，都會呼叫 1 次來**優化計劃** (`plan_refine_agent`)。
    -   **如何修改**: 減少 `num_solutions`、`outer_loop_round` 或 `inner_loop_round`。

-   **`A_ensemble` (整合)**:
    -   **呼叫次數**: `1 (初始計劃) + ensemble_loop_round (優化計劃) + 每次實作的呼叫 + 除錯次數`。
    -   **如何修改**: 減少 `ensemble_loop_round`。

**總結**:
LLM 的總呼叫次數是一個複雜的計算，主要由以下因素決定：
1.  **配置參數**: `num_solutions`, `outer_loop_round`, `inner_loop_round` 是最主要的乘數因子。
2.  **程式碼品質**: LLM 生成的程式碼 bug 越多，用於除錯的額外呼叫就越多。
3.  **Agent 設計**: 代理程式的循環邏輯決定了基礎呼叫次數。

要**修改呼叫次數**，最直接的方法就是**調整 `pyproject.toml` 或相關設定檔中的 `num_solutions`、`outer_loop_round` 和 `inner_loop_round` 參數**。

### 12. 如果需要設定為不同 LLM，請給予不同等級 (1-5)。
如果可以為不同代理程式設定不同能力的 LLM，可以根據它們任務的複雜度來分配，以平衡成本和效果（等級 5 為最高能力、最昂貴）：

-   **`A_retriever` (模型檢索員)**:
    -   **等級: 3**
    -   **需求**: 需要良好的語言理解能力來解析任務描述，並具備一定的知識廣度來生成有效的搜尋關鍵字。但它不直接生成複雜的程式碼，所以不需要頂級模型。

-   **`A_abl` (消融研究員)**:
    -   **等級: 4**
    -   **需求**: 需要較強的程式碼理解能力。它必須能讀懂整個訓練腳本，並準確地移除或註解掉某個邏輯區塊而不破壞程式的整體結構。這比單純的程式碼生成更需要上下文理解。

-   **`A_extractor` & `A_planner` (分析師與計劃員)**:
    -   **等級: 5 (最高)**
    -   **需求**: 這是整個流程中**最具創造性和分析性**的環節。LLM 不僅要理解消融研究的結果，還要基於這些結果進行**策略性思考**，提出具體、可行且有創意的改進計劃。這非常接近人類專家的工作，需要最強的推理和規劃能力。

-   **`A_ensemble` (模型整合專家)**:
    -   **等級: 5**
    -   **需求**: 與 `A_planner` 類似，需要高度的策略性思考。它要分析多個複雜模型的優劣，並設計出非凡的組合策略。這同樣需要頂級的推理能力。

-   **程式碼生成與除錯代理程式**:
    -   **等級: 4**
    -   **需求**: 需要非常強的程式碼生成和修復能力。雖然任務目標明確（實現某個計劃或修復某個 bug），但需要產出語法正確、邏輯無誤的程式碼，對模型的要求很高。

**總結建議**:
-   **最高級 (5)**: 分配給 `A_planner` 和 `A_ensemble`，因為它們負責「思考」和「決策」。
-   **次高級 (4)**: 分配給 `A_abl` 和程式碼生成/除錯器，因為它們需要高質量的程式碼操作。
-   **中級 (3)**: 分配給 `A_retriever`，任務相對明確，對創造性要求較低。

### 13. 什麼是「獎牌率」？「43.9%」與「63.6%」代表什麼？
「獎牌率 (Medal Rate)」是 `README.md` 中用來衡量 MLE-STAR 性能的指標，源自 Kaggle 競賽的獎牌系統。

在 Kaggle 競賽中，排名前列的隊伍會根據其最終排名獲得金、銀、銅牌。獲得任何一枚獎牌都意味著其解決方案在所有參賽者中達到了非常高的水平。

-   **獎牌率的意義**:
    `README.md` 中的表格是在一個名為 `MLE-Bench-Lite` 的基準測試集上評估的結果。這個測試集包含了很多個來自 Kaggle 的真實歷史任務。**「獎牌率」指的就是，MLE-STAR 在這批任務中，其自動產生的解決方案能夠達到獲獎水平（金/銀/銅牌中任意一種）的任務佔總任務的百分比。**

-   **「63.6%」的意義**:
    -   這代表當使用 **Gemini 2.5 Pro** 作為背後的 LLM 時，MLE-STAR 在 `MLE-Bench-Lite` 測試集的所有任務中，有 **63.6%** 的任務上，其自動生成的模型達到了可以獲得獎牌的水平。這是一個非常驚人的數字，說明其自動化解決方案的質量在超過一半的真實競賽任務中都能排進前列。

-   **「43.9%」的意義**:
    -   這代表當使用 **Gemini 2.5 Flash**（一個更輕量、更快的模型）作為 LLM 時，MLE-STAR 的獎牌率為 **43.9%**。

**數字大小的比較**:
`63.6%` (使用 Pro) > `43.9%` (使用 Flash)。這個對比說明了：**使用更強大、更「聰明」的 LLM，可以讓 MLE-STAR 代理程式產生更高質量的解決方案，從而在更多任務上獲得獎牌。** 這也驗證了 LLM 的能力是整個系統性能的關鍵。

## 第三部分：補充說明

### 針對專案還有哪些需要補充說明的部分？

1.  **對網路環境的依賴**:
    -   `A_retriever` 代理程式在初始化階段需要**訪問 Google 搜尋**來查找模型和範例。在網路受限的環境下，如果無法訪問外部網站，這個步驟會失敗，導致整個流程無法啟動。這可以透過設定代理 (proxy) 來解決，但需要確保代理能訪問到 Google。

2.  **隨機性的影響**:
    -   LLM 的回覆本身帶有一定的隨機性（即使溫度設定為 0，也可能因模型版本更新等因素變化）。
    -   機器學習模型（如 RandomForest）的訓練過程也包含隨機性。
    -   因此，兩次完全相同的運行，最終產生的程式碼和分數也可能存在微小差異。專案中透過 `set_random_seed` 來盡可能地控制這種隨機性，以保證結果的可複現性。

3.  **可擴展性**:
    -   整個專案的框架是高度模組化的。要解決一個新的任務，使用者只需要在 `tasks` 目錄下創建一個新的資料夾，放入數據和任務描述即可，無需修改核心程式碼。
    -   可以相對容易地增加新的代理程式（例如，一個專門做數據視覺化和分析的代理程式）來擴展系統的能力。

4.  **成本考量**:
    -   如前所述，執行一次完整的流程會進行大量的 LLM API 呼叫，這會產生費用。調整 `num_solutions` 和 `*_loop_round` 等參數是控制成本的關鍵。

5.  **與 Auto-ML 的區別**:
    -   傳統的 AutoML 工具（如 Google Cloud AutoML）通常是一個黑盒子，它會自動幫你找到最好的模型，但你無法看到或修改中間的程式碼。
    -   MLE-STAR 的最大優勢在於它最終會**產出一份人類可讀、可修改、可直接使用的完整 Python 程式碼**。它不僅給了你「魚」（預測結果），還給了你「釣竿」（訓練程式），並教你如何「釣魚」（優化過程記錄在 workspace 中）。
